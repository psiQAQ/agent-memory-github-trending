## 调度与状态

ChatGPT 任务名称为 `Agent Memory 追踪`，周期为每 12 小时。任务已在本次初始化中创建并暂停；未运行。任务的账户级 ID 不写入公开仓库。

启用需要同时满足：用户确认方案、配置 approval_state=approved、implementation_ready=true、automation_enabled=true，以及 ChatGPT 任务恢复。周期任务不得自行更改这些门禁。恢复时重新设置从启用起的时间锚点，或采用用户确认的固定时段。

任务提示词必须明确读取本仓库 AGENTS、配置、方法、维护流程和状态；AGENTS.md 本身既不会创建定时器，也不保证 ChatGPT 自动加载文件。不得使用本次聊天附件或用户个人记忆作为运行所必需的状态。

## 一轮检查

1. 读取当前默认分支、HEAD、AGENTS、配置和状态；检查授权/实现就绪门禁与方法版本。
2. 用已完成 run_id 与当前时间槽判定重复执行；核对上次未完成发布，避免重复事件。读取逐项目游标和失败队列。
3. 优先处理到期重点项目及恢复队列；读取新的 GitHub 元数据、release、相关 PR/文档或代码差异。只有实质内容改变时进行深读。观察池按轮询预算处理。
4. 并行概念上执行候选发现通道，但不并行修改相同 GitHub 文件。记录查询覆盖和缺失；新候选必须先审查相关性，不能从搜索结果直接提升为推荐。
5. 生成时间戳快照、去重事件、必要的项目卡片变更。新快照允许重复数值；同一事件不得因多来源报道或重试而重复计数。
6. 仅在确有内容变化时更新技术简报/README；检查是否有已结束而未总结的 ISO 周并形成一次周报。
7. 运行已实现的验证：结构/必填字段、仓库身份、证据引用、实际时间窗口、覆盖率、事件唯一键、文档长度和写入路径。验证能力不存在或执行失败时停止发布。
8. 用最新 base tree 生成数据提交，保持无关文件，非强制更新默认分支。分支保护或审批阻止时报告，不改保护设置绕过。
9. 回读数据提交内的关键文件，验证 run_id、数据与提交 SHA。验证通过后另写简短状态回执，保存已验证的数据提交 SHA；避免让文件包含自身提交 SHA 的循环依赖。
10. 按通知策略说明重要变化、源链接、数据提交和覆盖限制。普通计数快照不生成通知。首个真实定时运行无论是否发现新变化，都给出读写/校验验收结果。

## 故障处理

单个上游失败：保留上次成功观测，标记 stale，不覆盖成 0/null 冒充成功。记录本轮失败字段与时间；该来源游标不前进。其他来源允许以明确 partial 状态发布。

权限或 GitHub 写入失败：停止发布，报告实际错误；不改 app 权限、不创建额外任务、不切换到收费服务。当前会话写入成功不保证未来每次任务运行成功。

提交冲突：重新读取 HEAD 与状态，重算差异后最多重试一次；仍冲突则退出，不强推。

写入返回不确定或回读失败：下轮先查 run_id/提交记录；不得盲目重复追加。成功游标只在对应数据可确认已持久化后推进；状态回执失败时可据数据提交恢复。

抓取预算不足或分页不全：记录未覆盖项目和来源，入队后续轮询；不把本轮写成全量成功。通过固定样本和时间窗口规避覆盖变化导致的虚假趋势。

无变化：保留新数值观测及检查回执，不更新技术摘要、不凑新闻。任务平台是否发出系统完成通知取决于账号通知设置，本策略控制的是研究通知内容。

## 文档更新约定

README 与 latest 为当前视图；项目卡片仅更新变化段。事件和快照按时间追加；更正须明确 supersedes 原事件，不能悄悄篡改旧证据。周报完成后固定，纠错以说明记录。运行日志记录状态/覆盖/错误，不存完整模型对话、长篇思考或重复 TODO。

流程和口径的调整不夹带在普通快照提交中。先形成可读差异与理由，再按用户批准范围由 GPT 实施。用户无需逐次维护项目表或手动执行检查。
