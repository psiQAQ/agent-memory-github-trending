# 项目偏好与编辑验收

来源：仓库所有者于 2026-10-15 提供的两份内容/网站审计及明确改进请求。每轮维护先读取本文；它细化读者体验，不扩大 AGENTS.md 的操作权限、费用、写入范围或数据验证语义。

## 读者优先

目标读者是选型、接入和研究 Agent Memory 的人，而非正在排查采集程序的维护者。简报回答“发生什么、影响谁、是否行动”；不把完整仓库清单或每次 HEAD 变化写成新闻。主题强调机制、依赖、权限、持久性、数据正确性和升级兼容性。错误码检查若影响持久化可信度值得记录，但应解释风险，不能包装成算法突破。

每份简报固定为：三行要点 → 已确认合并/发布的变更表 → Star 变化 → 新候选对比 → 一段方法与边界。三行分别写最重要变化、受影响者、建议行动；没有足够证据就明确写“本轮没有足够证据建议迁移/升级”，不强造结论。尚未闭合的自然周不得称整周回顾。

变更表含项目、变化、已发布/已合并未发布、影响面及行动；每条都能追溯到一手 PR/Release/具体实现。标题采用“已确认合并/发布的变更”，不用暗示运行时验收的“验证有效/已核实效果”。静态代码阅读、上游自述、独立复现分别标记，厂商评测不等于独立认证。相同边界只写一遍；某项独有风险仍应紧邻结论保留。

## 数据与比较

简报必须给出真实 Star 观测表，或说明缺失原因和条件性的基线可用日期。缺乏 7/30 日合格基线时，可比较两次真实观测，但标题须写实际区间，列出起止时刻和经过时长，不外推成日/周增量。时间窗口容差仍为 ±6 小时。预计日期是“若届时采集成功”的条件，不是承诺；也不是数据开始记录日期。

分类内比较，不以总 Star 排跨类别质量榜；关注度变化不证明技术更好，也不能仅凭增长/下降判定刷榜。异常只标记“需核查”，附原始时段和证据；目前没有可靠的自动刷 Star 识别器。

正式项目及候选的横向表优先使用存储/记忆载体、检索与维护、依赖、宿主、评测资产、许可证、成熟度和版本。未知写“未核实”，有代码路径不等于评测有效或生产可用；观察版本不冒充“最新提交”。Token、质量、费用、延迟的数值需同时给出数据集、模型、配置、协议、版本与证据等级；不兼容协议不横排。

结构化路线说明保存在 reports/landscape.md，可按已登记一手证据修订；功能层可重叠。时间线只纳入可定年、可引用的事件，区分发生/发布/首次观察日期，不编造整个领域的起点。

## 读者内容与维护记录分离

运行 ID、完整 UTC/commit、分页截断、事件回填、任务管理页故障等放在 state/、运行指标或证据折叠区。简报正文仅保留会改变读者判断的一句覆盖范围；不要删除或覆盖历史 snapshot、原始证据或成功水位。

完整 PR、commit、文件链接和时间戳放在 `<details markdown="1"><summary>证据与时间</summary>` 中，默认折叠。简报首屏不要被 SHA 淹没。少用“水位/回灌/pinned HEAD”等词；必须使用时链接 docs/glossary.md。

外部榜单仅在方法、版本或有关结论发生实质变化时进入简报；未变化的榜单留在 docs/references.md，说明其发现/方法对照用途。原始 JSON 已开放，不宣称另外建立了实时后端 API；导出 CSV 不填补不存在的日期。

## 静态阅读与发布

GitHub Pages 原生 Jekyll 在发布阶段把原 Markdown 转成独立 `.html` 页面；保留原始 `.md`、JSON 和交互式 dashboard.html。Scheduled 仍只通过 GitHub API 更新原始内容，不运行 Jekyll/Ruby/Node/Python、不新增采集调度器。不要恢复 `.nojekyll`，它会关闭静态生成；站点框架修改仍需单独授权。

`reports/latest.md` 是首页摘要与最新阅读页的唯一正文源；“## 已确认合并/发布的变更”之前的三行要点自动进入首页。新简报发布时，同一 Data commit 内在 `reports/briefs/<run_id>.md` 保存一份内容等价的日期版本；第一次迁移已有 `reports/briefs/2026-10-15.md`。不要保留相对路径错误：briefs 子目录副本需把面向仓库的相对链接调整一级，或用经过核实的固定版本 GitHub 来源链接。同 run_id 历史稿不得覆盖。周报维持现有路径，静态归档自动发现，不需要复制 HTML。

静态正文和导航必须在禁用 JS 时可读；JS 只增强 TOC、进度、主题、复制链接和 CSV。深浅色支持系统默认与手动切换；窄屏只允许表格区域横向滚动，不让整个页面溢出。链接应为真实 `.html` 路径；旧哈希入口仍可跳到仪表盘或静态文档。

Markdown 不粘贴上游可执行 HTML 或 Liquid 模板；只允许经过审查的 details/summary 等展示标签，代码用围栏并转义模板定界符。保留 CSP，不加入外部脚本、跟踪像素或远程字体。

## 统一视觉外壳（2026-10-16）

全站以原趋势 Dashboard 风格为视觉基准：深色固定侧栏、明亮顶部栏、浅灰背景、青绿色强调、白色细边框信息卡、相同字重/按钮以及移动端抽屉导航。首页、静态简报和所有项目/方法页面复用 `_layouts/reader.html` 中的 Dashboard 导航壳层；共享视觉变量、布局来自 `assets/site.css`，正文类型排版仍由 `assets/reader.css` 保留，阅读页差异收敛于 `assets/reader-unified.css`。不要再创建另一套白色 masthead / 米色编辑式风格。

深浅主题与 Dashboard 共用 `localStorage.am-theme`（light/dark），没有显式偏好时遵循系统设置；阅读页 JS 只处理本页抽屉、目录、进度、复制链接，不得在 Dashboard 已有菜单上重复绑定，避免双击事件抵消。保留无 JS 静态正文与真实 `.html` 链接，所有页面的 CSS 资源均通过 Jekyll `relative_url` 适配项目路径；不得改动采集定时任务、原始 JSON 或历史研究记录。每次改样式应核对至少：首页、文章、Dashboard、暗色、窄屏、菜单键盘退出和宽表格局部滚动。

## 不直接采纳的建议

不因这次审计自动安装 MCP、运行上游 benchmark 或调用付费模型。可先整理公开评测协议；真正实验需要另行批准范围、数据、预算、环境和成功标准。没有实测就不发布节省 Token、召回率或成本下降数值。候选仍不设全局 Star 门槛，也不为凑数量自动晋升。

## 每轮验收

发布前检查：三行要点可独立读懂；每项有记录理由与状态；Star 表有真实起止时刻；候选可横比且未知没有被补造；重复免责声明已合并；运维细节不占正文；证据可展开；最新稿与日期稿一致；内部链接可解析。API 调用、来源覆盖、深读率与 Data/Receipt 回读继续按现有数据契约验证，不能以“文章更易读”替代完整性检查。

README 面向使用者，仅保留网站、用途、入口、方法、数据与维护文档链接；不再放首次 Pages 启用步骤、“尚未上线”等过时提示。故障通知仍以一句话写明环节、已知原因、可执行办法与真实 Data SHA；不自动改动每日北京时间 00:00 调度。
